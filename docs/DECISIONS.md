# RodAI Decision Log

No architecture or product decisions have been approved yet. The following are proposals for Phase 0 review, not binding decisions.

| ID | Proposal | Reason | Alternatives | Approval | Date |
|---|---|---|---|---|---|
| P0-1 | Start with a localhost-bound modular monolith: FastAPI backend and React/TypeScript/Vite frontend, with one backend-owned processing pipeline. | Matches the master prompt while keeping deployment simple and local-first. | Different stack or split services; no evidence presently justifies the extra complexity. | Pending owner approval | 2026-11-12 |
| P0-2 | Use Python 3.12 for the project environment, subject to a clean install/compatibility check; retain Python 3.13 on the host if needed. | Installed Python is 3.13.2, while current PyTorch Windows install guidance names Python 3.9–3.12. | Python 3.13 only if a supported compatible PyTorch stack is demonstrated; Linux/WSL only if Windows compatibility fails and owner approves. | Pending owner approval | 2026-11-12 |
| P0-3 | Default to one active session; uploaded video uses ordered lossless frame delivery, while live preview uses bounded newest-frame-wins delivery with explicit drop counts. | Prevents silent loss in offline analysis and unbounded latency in live preview. | Multiple sessions or another transport/queue strategy; hardware and workload are not yet known. | Pending owner approval | 2026-11-12 |
| P0-4 | Use file-based JSONL session results and metadata, with no database in v0.1. | Fits the stated local-first scope and preserves inspectable exports without database overhead. | SQLite if restart-persistent searchable history is required. | Pending owner approval | 2026-11-12 |
| P0-5 | Do not lock the detector/library/weights until licensing preference and actual hardware are known; benchmark at least two sizes during Phase 3. | Detector package and weight licensing can affect distribution; performance cannot be inferred from this environment. | Ultralytics (AGPL-3.0 or commercial licence) or a separately verified permissive implementation/model such as original RT-DETR (Apache-2.0 repository). | Pending owner approval | 2026-11-12 |
| P0-6 | Proposed frame transport: binary WebSocket JPEG frames with client capture timestamp and monotonic frame ID; backend echoes both and processes the same frame ID. | Reasonable browser-to-local-backend path; allows frame/overlay alignment without large JSON/base64 overhead. | WebRTC, multipart HTTP, or raw formats; select only after owner context and Phase 2 measurements. | Pending owner approval | 2026-11-12 |
| P0-7 | Proposed result transport: versioned JSON WebSocket messages (`rodai.v1`) carrying type, session/frame IDs, client and server timestamps, state, detections/tracks/events when implemented, and structured errors; heartbeat and reconnect behavior to be specified before Phase 2. | Makes the protocol explicit, versionable, and frame-aligned. | Polling or another protocol; no current requirement suggests it. | Pending owner approval | 2026-11-12 |
| ADD-1 | Railway is the deployment target; package with Dockerfile, use Docker Compose locally, and use Railway PostgreSQL plus a persistent app volume in deployment. | Explicitly decided in the owner-provided addendum. | No alternative is proposed unless owner revises the addendum. | Owner supplied addendum | 2026-11-12 |
| ADD-2 | Production inference is CPU-only; training/heavy experiments stay off Railway. | Explicitly decided in addendum; avoids depending on unverified GPU hosting. | None unless owner revises the addendum. | Owner supplied addendum | 2026-11-12 |
| ADD-3 | Use PostgreSQL with SQLAlchemy 2.x and Alembic in deployed app; prefer the same PostgreSQL engine in Compose to prevent drift. | Addendum establishes persistence need; DB stores metadata while JSONL/video files remain on volume. | SQLite locally only if owner explicitly chooses simplicity and accepts drift. | Pending local-development preference | 2026-11-12 |
| ADD-4 | Serve built frontend and FastAPI from one Railway service/origin by default; retain separate frontend as an alternative only if independent scaling/CDN is desired. | Simplifies same-origin API/WebSocket and deployment. | Separate service. | Pending owner preference | 2026-11-12 |
| ADD-5 | Public deployment requires real authentication, origin checks, quotas/rate limiting, secure secret handling and privacy controls before exposure. | Explicit addendum security requirement. | Provider identity integration only with separate approval. | Owner supplied addendum; implementation design pending audience | 2026-11-12 |
| ADD-6 | Use environment variables validated with Pydantic Settings; Docker base images and dependencies pinned; production image non-root and CPU-only. | Explicit addendum operational requirement. | None unless owner revises addendum. | Owner supplied addendum | 2026-11-12 |

Proposals P0-3 through P0-7 are preliminary. Addendum decisions ADD-1, ADD-2, ADD-5 and ADD-6 are owner-provided requirements. Local database preference and frontend service layout (ADD-3/4), detector licensing, privacy, data and hardware-affecting choices still require owner confirmation.
